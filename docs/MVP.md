## 1. 目标

MVP 只用一句话定义成功标准：

> 把一本 TXT 导入进来，能舒服地从头读到尾，关掉页面再打开还停在原处。

**本版只验证「第一次阅读」能不能完成。** 书签、笔记、搜索都属于「第二次阅读」的需求，排在后面。

### 已确认的边界

| 项 | 决定 |
| --- | --- |
| 平台形态 | Web / PWA，后续可套 Tauri 壳 |
| 数据位置 | 本地优先，无账号、无服务端 |
| 支持格式 | 仅 TXT |
| 范围 | 最小可用：能导入、能读、能记住位置 |
| 目标场景 | 自用 / 小范围 |

## 2. 段落与章节：先说清这两个概念

| 概念 | 在 TXT 中的形态 | 实现成本 | 结论 |
| --- | --- | --- | --- |
| 段落 | 换行符分隔的纯文本 | 几乎为零 | 不需解析：按换行切段，CSS 处理首行缩进与段距 |
| 章节标题 | 独占一行的纯文本，如「第一章 穿越」 | 一个正则，约 10 行代码 | **必须做**，见下 |

章节切分不可省，它是四件事的地基：

1. 目录跳转 —— 5MB 的 TXT 约 250 万字，没目录就无法回到第 37 章
2. 按章渲染 —— 性能命脉，不允许把百万字整块塞进 DOM
3. 可理解的进度 —— 「第 37 / 220 章」比「12.4%」有用
4. 位置恢复 —— 章节索引 + 章内偏移比全局偏移更稳

## 3. 本版 P0：最小可用范围

只有五块，做完就是一个能用的阅读器。

**3.1 导入与解码**

- 文件选择 + 拖拽，支持一次多本
- 书名从文件名清洗得出（处理「《书名》作者.txt」「书名(完结).txt」等噪音）
- 编码识别：BOM → 严格 UTF-8 → 失败回退 GBK
- 解码失败或疑似二进制文件时给明确提示，不白屏
- 验收：GBK 编码的中文 TXT 导入后不乱码

**3.2 章节切分**

- 逐行正则识别标题行，覆盖常见形态：
    ^\s*第\s*[0-9零一二三四五六七八九十百千万两]+\s*[章节回卷部篇集]
    ^\s*(序章|楔子|序言|前言|引子|后记|尾声|终章|番外)
- 识别不到章节时按每 3000–5000 字定长分片兜底，并明确标注为「分段」
- 每章记录标题、起始偏移、字数
- 验收：典型网络小说 TXT 能切出正确的章节数与标题

**3.3 书架**

- 列表展示：书名、阅读进度、最近阅读排序
- 删除、重命名
- 验收：导入 3 本后刷新页面，内容与顺序不变

**3.4 阅读界面**

- 滚动流阅读（不做分页）
- 只渲染当前章，上一章/下一章切换
- 目录抽屉：章节列表、当前章高亮、点击跳转
- 排版：字号、行距（两项即可）
- 主题：白天 / 夜间
- 验收：切章无卡顿；调字号后正文重排且位置不丢

**3.5 进度**

- 保存「书籍 ID + 章节索引 + 章内字符偏移 + 总百分比」
- 跨会话恢复，书架显示百分比
- 验收：读到第 5 章关掉浏览器，重开落在第 5 章同一句话附近

## 5. 什么可以推迟，什么不能推迟

判断标准：

> 新功能如果只是「加一张表 / 加一个可空字段 / 纯读现有数据」——随时可以推迟。
> 如果需要「修改已有字段语义 / 重新解析用户已导入的书 / 让用户重导一次」——必须现在做对。

按此标准：

| 项 | 类型 | 能否推迟 |
| --- | --- | --- |
| 书签、划线、笔记 | 新增表 | 可以 |
| 章节内搜索 | 纯读现有正文 | 可以 |
| 阅读统计、PWA、分页模式 | 独立模块 | 可以 |
| EPUB | 需 Book.format + 解析器接口 | 接口现在留（成本≈0），实现可推迟 |
| **进度锚点的字段结构与语义** | 有用户数据后改动需迁移 | **现在必须定对** |

### 砍不掉的地基

功能列表可以很短，但下面这些是真实工作量，不属于「功能」，无法通过砍范围去掉：

| 地基 | 为什么砍不掉 |
| --- | --- |
| 编码识别（GBK/UTF-8） | 做错了整本书是乱码 |
| 章节切分 + 兜底 | 正则失配时不能让书变成一整块 |
| 大文件性能 | 百万字不能整块进 DOM，必须只渲染当前章 |
| 进度锚点 | 存页码则一改字号进度就废 |
| 错误处理 | 坏文件不能白屏 |

## 6. 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 构建 | Vite + React + TypeScript | 反馈循环最短 |
| 状态 | Zustand（或轻量 Context） | 不引入重型状态框架 |
| 编码 | BOM 优先，严格 UTF-8 失败则回退 GBK（原生 TextDecoder 支持 gbk） | 零依赖解决中文乱码 |
| 章节切分 | 自研逐行正则 | 逻辑简单、完全可控、易测试 |
| 本地存储 | IndexedDB（idb 封装） | 适合大文本对象与配额管理 |
| 样式 | CSS 变量驱动主题与排版 | 主题切换无需重渲染 |
| 单元测试 | Vitest | 覆盖编码识别、章节切分、进度锚点、文件名清洗 |
| 端到端测试 | Playwright | 覆盖导入 → 阅读 → 进度恢复 |

> 桌面壳、进程模型与平台抽象层的完整方案见 [TECH.md](TECH.md)。形态已由 Web/PWA 调整为 Electron 桌面应用。

## 7. 数据模型（属于地基，本版就要定对）

    Book {
      id, title, author?, format: 'txt',
      coverSeed, size, charCount, chapterCount,
      encoding, addedAt, lastOpenedAt
    }

    Chapter {
      bookId, index, title, startOffset, charLength
    }

    Progress {
      bookId, chapterIndex, charOffset, percent, updatedAt, deviceId?
    }

设计约束：

- 正文单独存储，Chapter 只存偏移与长度，不重复存正文
- 保留 format 字段与解析器接口：将来接 EPUB 不改数据层
- Progress 从第一天带 deviceId，为同步预留，本版不实现
- Annotation（书签）表本版不建，将来新建即可，不影响上述结构（0.1.3 已按此结果落地：schema v2 新增 `bookmark` / `highlight` / `reading_stat` 三张表，上面几个既有字段一个没动）

## 8. 关键设计决策与坑

1. **进度用文本锚点，不用页码** —— 存章节索引 + 章内字符偏移，预留「前文 30 字 + 后文 30 字」引文锚点兜底
2. **只渲染当前章** —— 跨章边界要处理「上一章末尾」的衔接
3. **章节切分必须有兜底** —— 正则失配时退回定长分片，绝不能因为没章节就渲染不出来
4. **章节 vs 分段要在文案上区分** —— 定长分片不能号称是「章节」，否则误导用户
5. **存储配额** —— 大 TXT 累积快，配额满要有提示与清理入口
6. **文件名清洗** —— 书名噪音规则要单独写测试

### 格式路线图（长期方向，2026-10-06 用户圈定）

用户原则原话：「一个一个来吧，尽量优化。先加入目标。留好接口，为以后做铺垫。尽量不把路子堵死。」

**判断格式要不要做的唯一标准**：这个应用的地基是**「纯文本 + UTF-16 字符偏移」** —— 进度存「章内第 N 个字」，书签、划线、搜索全锚在字符偏移上。所以一个格式**能不能被拆成「带章节结构的纯文本」**，决定了它能不能接进现有管线。能 → 增量小；不能 → 等于再写一套阅读引擎。

**接口要留什么**（做 0.2.0 时就顺手铺好，不额外增加多少工作量）：

1. `BookFormat` 联合类型扩成 `'txt' | 'epub' | 'mobi' | 'md' | 'pdf'`（`src/shared/types.ts`），schema 里 `format` 列本来就是 `TEXT`，不用迁移。
2. 导入管线按**扩展名**分派到「提取器」函数，提取器统一签名：`(bytes) => { text, chapters, images? }`。EPUB 的第一个实现顺便把这个形状定死，后面 MOBI / MD / PDF 照着填。
3. 提取器实现放 `src/main/services/<format>/`，与 `epub/` 平级；能纯函数化的（MD、FB2）放 `src/shared/core/`。
4. `book:redecode` 的等价物：对非 TXT 格式，「重新解码」= 「按最新提取器重新提取」，复用 `source.bin` —— EPUB 阶段就把这个语义定好。
5. 书架卡片目前**不显示格式**（只有编码徽标 `{book.encoding.toUpperCase()}`）。等真的支持第二种格式时再加，避免现在多一个没信息的角标。

**分档与理由**（不是为了劝退，是把预期摆正）：

| 档 | 格式 | 判断 | 依据 |
| --- | --- | --- | --- |
| 低 | **Markdown (.md)** | 几乎零成本，纯文本直通 | 走现有 TXT 管线，只需对话框放行后缀 + 文件名清洗告知 .md |
| 低 | HTMLZ / 单文件 HTML | 与 EPUB 的单章 XHTML 提取同源 | EPUB 阶段写好的 `xhtml-text` 直接复用 |
| 低 | FB2 (.fb2) | XML，提取逻辑近似 XHTML | 俄罗斯电子书标准；先不管，看到再说 |
| 中 | **MOBI / AZW3**（0.3.0 首选） | 可做，但解包比 EPUB 复杂 | 容器是 PalmDOC / MOBI header + 记录索引；拆开后内部仍是 HTML，正文提取复用 EPUB 那套。无 DRM 的 .mobi 可行 |
| 中 | DOCX | 能提取，但丢掉排版 | ZIP + XML（`word/document.xml`），`w:pStyle` 为 Heading 可当章；等于「当 TXT 用」 |
| 高 | **PDF（文字层）** | 只做「有文字层的 PDF」 | 有文字层的 PDF 可用 `pdfjs-dist` 抽文本，但**永不可重排**（固定版面坐标）。定位为「文字用能用的阅读器」：段落靠坐标聚类还原，缩进/表格/分栏不可靠，**不承诺排版保真**。产品上给独立提示，不与 TXT/EPUB 同待遇 |
| 不做 | 扫描件 PDF | 无文字层，本质是图片 | 报「这是扫描件，读不了文字」；OCR 不在规划内 |
| 不做 | 漫画 (CBZ/CBR) / DjVu | 图像为主，是另一个产品 | 与文字阅读器正交 |
| 不做 | DRM 加密书（含加密 EPUB/MOBI） | 法律与技术双重障碍 | 明确报「此书有版权保护，打不开」 |

**实施节奏**：**0.2.0 = EPUB（在做）；0.3.0 = MOBI；之后按实际使用需求逐个评估 Markdown / PDF**。每上一个格式前，先拿真实书实测，再决定要不要动。

**明确不堵死的三个点**：① 提取器接口从 EPUB 起就按「可插拔」设计；② `format` 字段与 `images.json` 这类派生清单都能容纳新格式；③ 阅读器渲染层对「纯文本 + 可选内联图片」的假设已经够宽，PDF / MOBI 不需要推翻它（PDF 若真要保真另开产品线，不往这里塞）。

**A. 窗口尺寸 / 位置记忆 —— 已完成（2026-10-07）**

一句话：**你调过的窗口大小与位置，下次打开还在原处。**

原状：`src/main/window.ts` 里 `width: 1180, height: 800` 写死，不读写窗口 bounds —— 把窗口拖大、挪到副屏，重开就回到默认。

落地做法：

- 纯函数 `src/shared/core/window-bounds.ts`：`parseWindowState()` 防脏数据（形状不对一律当没存过）；`resolveWindowBounds()` 三条规则 —— ① 没存过 → 默认尺寸、位置交给系统居中（不写 x / y）；② 坐标已失效（与任一屏幕工作区重叠不足 120×40，或标题栏被顶到屏幕上边之外）→ 保留夹取后的尺寸、丢位置交给系统居中；③ 尺寸一律夹到 `[最小 760×540, 最大屏]`。`minWidth / minHeight` 也改从 core 常量取，避免与校验两处漂移。
- 存哪儿：`meta` 表的 `window_state` 键 —— 与阅读设置同一张表、同一套机制，**不新增数据文件**；实现是 `src/main/services/window-state.ts` 的 `WindowStateStore`。
- 写时机：**只在窗口 `close` 写一次**，不做 resize / move 防抖（少一次写库；代价是进程被强杀时丢本次调整，可接受）。
- 最大化：`captureWindowState()` 用 `getNormalBounds()` 取「还原后」的尺寸，重启时先建窗口再 `maximize()`。
- 屏幕信息只在建窗口前取一次（`screen.getAllDisplays()`）。

测试：单测 `tests/unit/window-bounds.test.ts`（16 例：脏数据 / 屏外回退 / 标题栏顶出 / 重叠不足 / 尺寸夹取 / 多屏不被小屏压扁 / 最大化两条路都保留）+ `tests/unit/main-stores.test.ts` 补 5 例（存取、坏 JSON、坏形状、`getNormalBounds` 语义）；e2e `tests/e2e/window-state.spec.ts`（改尺寸 → 重启 → 尺寸与位置保持；最大化 → 重启 → 仍最大化）。

不做：书架 / 阅读器分别记尺寸（一个窗口一套 bounds 就够）；窗口置顶、迷你窗（见候选池）。

一句话成功标准：**导入一本 EPUB，像 TXT 一样读 —— 切章、翻页、进度、书签划线、搜索、统计、备份全链路零区别；打不开的书（损坏 / 加密 / 空壳）给明确中文提示，绝不白屏。**

核心思路（架构切入点）：EPUB 导入本质是给解码管线加一条新路径 —— `decode-job` worker 里多一个 `.epub` 分支：ZIP 解包 → OPF / spine / 目录解析 → 逐章 XHTML 提取纯文本，最后产出与 TXT **同一形状**的 `DecodeJobResult`（连续正文 + 章节表 + UTF-16 偏移）。进度锚点、书签划线、搜索、统计、备份全部只认「章节表 + 偏移」，一个字不用改。schema v1 早已预留 `book.format` 字段（默认 `'txt'`），数据层零迁移。

用户拍板的两项（2026-10-06）：

- **ZIP 解包手写 lenient reader，不引依赖**：与 0.1.3 手写的 `zip-writer.ts` 对称成对。只覆盖读本地文件的基本盘：EOCD + 中央目录定位、STORE 与 DEFLATE（`zlib.inflateRawSync`）、data descriptor、UTF-8 文件名位；加密 ZIP 与 Zip64 明确报「不支持」而不是硬解。测试夹具直接用自家 zip-writer 生成，再手工构造怪 ZIP（缺中央目录、加密位等）补负例。
- **插图做内联渲染，用 U+FFFC 占位**：每张图在提取文本里占一个 Unicode「对象替换字符」（U+FFFC，BMP 内 1 个 code unit），偏移体系（进度 / 书签 / 划线 / 搜索）原样保住。提取时把图片资源落盘 `books/<id>/images/` 并生成 `images.json`（偏移 → 资源路径）清单；渲染层把 U+FFFC 原地替换成 `<img>`（限宽居中），图片走主进程注册的自定义协议安全加载，CSP 的 `img-src` 随之扩一项。搜索命中上下文里的 U+FFFC 显示为「[图]」。

| 3 | XHTML → 纯文本 | `epub/xhtml-text.ts`：块级元素切段落、`<br>` 断行、图片转占位符（alt 文字保留）、HTML 实体解码 | 段落格式与 TXT 管线完全一致，下游才零改动 |
| 4 | 导入管线接线 | `decode-job.ts` 按扩展名分支；`file:pick` 对话框过滤加 `epub`；拖拽接受 `.epub`；`book.format` 写 `'epub'`；书名 / 作者取 OPF metadata，缺失再退文件名清洗 | 二进制判定不得抢在 EPUB 分支之前 |
| 5 | 内联图片渲染 | 提取时落 `images/` + `images.json`；渲染层 U+FFFC → `<img>`；自定义协议 + CSP 扩 `img-src` | 见上方拍板 |
| 6 | 重新提取 | `book:redecode` 对 EPUB 等价于「重新提取」：复用 `source.bin` 重跑 2–4，清该书进度 | 提取逻辑修复后旧书能吃到；无编码选择项（EPUB 规范即 UTF-8/16 XML） |
| 7 | 备份兼容 | 清单记 `hasSource` 照旧；`images/` 是派生物，不进包（与 `content.txt` 同理） | 还原依旧不做 |
| 8 | e2e 与性能实测 | 自造 EPUB 夹具 + 真实书实测 | 见下方预算 |

不做（0.2.0 明确排除，防蔓延）：

- 书架真实封面 —— 封面继续用现有占位方案；真封面要动所有书的卡片 UI，与 EPUB 解码正交，留以后。
- EPUB 自带 CSS / 字体 —— 排版继续全走应用自己的设置（产品立场，不是偷懒）。
- 粗体 / 斜体等行内样式 —— 正文是纯文本管线，样式剥掉只留文字。
- 目录多级嵌套展示 —— nav 拍平成一级章列表（现目录抽屉是平的）。
- DRM 加密书 —— 明确报错「此书有版权保护，打不开」。
- 脚注弹窗、MathML、SVG 内嵌文本。

章节切分规则（EPUB 有显式目录，比 TXT 幸福）：

1. nav / NCX 顶层条目 → 章（标题取目录文本，位置映射到对应 spine item 的章内偏移）。
2. 无目录 → 每个 spine item 一章（标题取该章第一个 h1–h6，没有就「第 N 节」）。
3. 单个 spine item 巨大（整本一个 XHTML 的坏例子）→ 对提取出的文本跑**现有 TXT 正则切章**，再不行退定长分段（`kind: segment`，文案照旧区分「分段」）。

实施顺序：**1 → 2 → 3 → 4（接线）→ 5（图片）→ 6（重新提取）→ 7（备份）→ 8（e2e / 性能）**。前三步是纯函数 + 单测，不碰 UI 就能全部验证。

性能预算（以一本 5–10MB、几百章的真实 EPUB 为靶子实测）：

| 指标 | 目标 |
| --- | --- |
| 导入（解包 + 提取 + 落盘） | < 2s |
| 打开到首个段落 | < 500ms |
| 全书搜索 | 照旧 < 1s（扫提取后的正文，与 TXT 同一条路） |
| 切章 | 照旧 < 100ms |

测试策略：ZIP reader 正例用自家 zip-writer 生成、负例手工构造怪 ZIP；容器解析覆盖 EPUB2 / EPUB3 / 损坏 XML / 加密书；XHTML 提取覆盖实体、嵌套块级、`<br>`、图片 alt、CJK 与 emoji（偏移语义）；e2e 走「导入 EPUB → 读 → 切章 → 进度重启恢复 → 搜索 → 书签划线 → 带图章节渲染」全链路。真实书样本由用户提供（中文书优先）。
